Document Database Design Standards

Version: 3.0
Last Updated: Feb 2026
Scope: Commercial Production Systems

1. Design & Review Checklist

Use this checklist for every new collection or major schema change. Failure to address these points typically results in technical debt or production incidents.

Data Modeling & Schema
Access Patterns Defined: Have you explicitly listed the top 3 read queries and the primary write pattern? Schema design cannot proceed without this.
Unbounded Arrays Check: Are any array fields capable of growing indefinitely (e.g., logs, comments, history)? If yes, they MUST be moved to a separate collection (Referencing).
Cardinality Check: For 1-to-Many relationships, is the "Many" side <100 (Embed), <1000 (Subset/Bucket), or >1000 (Reference)?
Document Size Limit: Is the maximum estimated document size comfortably under the 16MB hard limit (aim for <4MB for performance)?
Integrity & Validation
Schema Validation: Is JSON Schema validation defined at the database level (not just application code) to prevent data corruption?
Transaction Strategy: Does the operation require ACID guarantees across multiple documents? If yes, are Multi-Document Transactions enabled and handled correctly in code?
Enum Enforcement: Are status fields (e.g., `pending`, `active`) restricted to a strict Enum list in the schema validator?
Performance & Indexing
ESR Rule Applied: Do all compound indexes follow the Equality -> Sort -> Range field order?
Covered Queries: For high-frequency reads, does the index cover all projected fields to avoid fetching the document from disk?
Write Performance: Are there too many indexes? (Rule of thumb: >5 indexes on a write-heavy collection requires justification).
Security & Lifecycle
Field-Level Encryption: Is PII (Personally Identifiable Information) encrypted via CSFLE?
Data Lifecycle (TTL): Is there an automatic deletion (TTL index) or archival strategy for old data?

2. Core Design Principles

Unlike RDBMS where normalization is the priority, Document DB design prioritizes read performance and data locality.

The Golden Rules

  1. Together is Better: Access patterns dictate structure. If you read data together, store it together (Embedding).
  2. Avoid Unbounded Arrays: If a child array can grow indefinitely, do NOT embed. Use References.
  3. Duplication is Acceptable: Duplicating data (e.g., `user_name` inside an `order`) to avoid `$lookup` (joins) is standard practice in high-scale systems.

4. Security & Cyber Considerations

NoSQL databases are often insecure by default. The following controls are mandatory for commercial deployments.

4.1 Injection Prevention

Risk: Passing unsanitized user input directly into query filters allows attackers to bypass logic.
Example Attack: Sending { "$ne": null } as a password field bypasses auth.
  • Control: Never construct query objects directly from `req.body`.
  • Control: Cast all inputs to their specific types (e.g., `ObjectId`, `String`, `Int`) before querying.
  • Control: Use an ODM (Mongoose/Typegoose) with strict schema validation.

4.2 Network & Encryption

Layer Requirement
Transport TLS/SSL 1.2+ mandatory for all connections. No plaintext connections.
At Rest Volume-level encryption (e.g., AWS KMS) enabled.
Field Level PII (e.g., `email`, `bank_details`) must use Client-Side Field Level Encryption (CSFLE) for GDPR compliance.

4.3 Role-Based Access Control (RBAC)

Do not use the `root` user for application connections.

  • Service Accounts: Create specific DB users with Least Privilege (e.g., `readWrite` on specific database only).
  • No Public Access: Database must reside in a private VPC subnet.

5. Performance & Indexing

Poor indexing is the #1 cause of Document DB outages.

5.1 The ESR Rule

When creating compound indexes, always follow the E.S.R. order:

  1. Equality: Fields matched exactly (e.g., `status: "active"`).
  2. Sort: Fields used to sort results (e.g., `created_at: -1`).
  3. Range: Fields used for range filters (e.g., `price: { $gt: 100 }`).

5.2 Working Set Management

Guideline: Your "Working Set" (frequently accessed data + indexes) must fit in RAM. If it exceeds RAM, disk I/O will severely degrade performance.

6. Schema Example: E-Commerce Order

Below is a production-ready JSON schema template including validation and documentation comments.

{
  "_id": "ObjectId('...')",
  "user_id": "ObjectId('...')", // Indexed. Reference to Users.
  
  // PATTERN: Bucket Pattern / Snapshot
  // Duplicate user details to freeze state at time of purchase.
  "customer_snapshot": {
    "name": "J. Doe",
    "email": "jdoe@example.com"
  },

  "status": "shipped", // Enum: [pending, paid, shipped, cancelled]
  "total_amount": 45.00,
  
  // PATTERN: Computed Pattern
  // Pre-calculate this to avoid summing line_items on every read.
  "item_count": 2, 

  // PATTERN: Embedding
  // Line items are bounded. Read/Written together with Order.
  "line_items": [
    {
      "sku": "PROD-001-BLK",
      "name": "Cotton T-Shirt - Black",
      "price": 15.00,
      "qty": 3
    }
  ],

  "audit_log": {
    "created_at": "ISODate('2026-02-18T10:00:00Z')",
    "updated_at": "ISODate('2026-02-18T14:30:00Z')",
    "ip_address": "192.168.1.5"
  }
}

7. Operational Excellence

  • Point-in-Time Recovery (PITR): Must be enabled to allow restoration to a specific second.
  • Schema Versioning: Add a `schema_version: Int` field to every document to handle migration logic in code.
  • Slow Query Logging: Enable profiling for queries exceeding 100ms.
