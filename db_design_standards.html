1. Design & Review Checklist

Use this checklist for every new collection or major schema change. Failure to address these points typically results in technical debt or production incidents.

Data Modeling & Schema
Access Patterns Defined: Have you explicitly listed the top 3 read queries and the primary write pattern? Schema design cannot proceed without this.
Unbounded Arrays Check: Are any array fields capable of growing indefinitely (e.g., logs, comments, history)? If yes, they MUST be moved to a separate collection (Referencing).
Cardinality Check: For 1-to-Many relationships, is the "Many" side <100 (Embed), <1000 (Subset/Bucket), or >1000 (Reference)?
Integrity & Validation
Schema Validation: Is JSON Schema validation defined at the database level to prevent data corruption?
Transaction Strategy: Does the operation require ACID guarantees across multiple documents? If yes, are Multi-Document Transactions enabled?
Security: Blind Indexing
PII Isolation: Are all PII fields (Email, NINO, Bank Details) encrypted before entering the DB?
Algorithm Check: Is the blind index using HMAC-SHA256 (or better) with a secure, rotated secret key? (Simple SHA256/MD5 are forbidden).
No Plaintext PII: Have you verified no PII exists in plaintext in the schema or logs?
Performance
ESR Rule Applied: Do all compound indexes follow the Equality -> Sort -> Range field order?
Covered Queries: For high-frequency reads, does the index cover all projected fields?

2. Core Design Principles

Unlike RDBMS where normalization is the priority, Document DB design prioritizes read performance and data locality.

The Golden Rules

  1. Together is Better: Access patterns dictate structure. If you read data together, store it together (Embedding).
  2. Avoid Unbounded Arrays: If a child array can grow indefinitely, do NOT embed. Use References.
  3. Blind Indexing for PII: Querying encrypted data requires a deterministic keyed hash. You index the hash, not the encrypted blob.

4. Security & Cyber Considerations

NoSQL databases are often insecure by default. The following controls are mandatory for commercial deployments.

4.1 Pattern: Blind Indexing (App-Side Encryption)

Requirement: PII must be encrypted before entering the DB. To allow searching (e.g., "Find User by Email"), we store a deterministic Blind Index.

Approved Algorithms Table

Use Case Recommended Algorithm Why?
Blind Indexing
(Searchable Hash)		 HMAC-SHA256 Mandatory: Requires a secret key (Pepper) stored in the App (Vault/KMS). Without the key, the hash cannot be brute-forced via Rainbow Tables. Fast enough for high-volume lookups.
Passwords
(Auth)		 Argon2id Memory-hard hashing prevents GPU cracking. Too slow for general indexing, but perfect for auth.
Encryption
(Storage)		 AES-256-GCM Standard symmetric encryption with integrity checks.
FORBIDDEN MD5, SHA1, Simple SHA256 Simple hashes (even with salt) are vulnerable to Rainbow Tables if the DB is leaked. Always use a Keyed Hash (HMAC).

Layer Requirement
Transport TLS/SSL 1.2+ mandatory for all connections. No plaintext connections.
At Rest Volume-level encryption (e.g., AWS KMS) enabled.

5. Performance & Indexing

Poor indexing is the #1 cause of Document DB outages.

5.1 The ESR Rule

When creating compound indexes, always follow the E.S.R. order:

  1. Equality: Fields matched exactly (e.g., `email_hash: "..."`).
  2. Sort: Fields used to sort results (e.g., `created_at: -1`).
  3. Range: Fields used for range filters (e.g., `price: { $gt: 100 }`).

6. Schema Example: Secure User Profile

Below is a production-ready JSON schema template demonstrating the Blind Indexing pattern.

{
  "_id": "ObjectId('...')",
  
  // PII FIELD: EMAIL
  // 1. Encrypted blob for display (randomized IV, cannot be queried)
  "email_enc": "BASE64_ENCRYPTED_BLOB...",
  // 2. Deterministic Hash for lookup (HMAC-SHA256 with Secret Key)
  "email_hash": "e3b0c44298fc1c149afbf4c8996fb924...", // Indexed

  "status": "active",
  
  // NON-PII fields can be plaintext
  "preferences": {
    "marketing_opt_in": true,
    "theme": "dark"
  },

  "audit_log": {
    "created_at": "ISODate('2026-02-18T10:00:00Z')",
    "ip_address": "192.168.1.5"
  }
}

Appendix A: Domain Case Study - Carer's Allowance

This case study demonstrates App-Side Encryption for a high-integrity domain. NINO and Bank Details are PII and must be encrypted before DB insertion.

A.1 Requirements & Access Patterns

  • Read 1 (Search): "Find Claim by Caree's NINO" (Requires Blind Index on NINO).
  • Read 2 (Display): "Show Bank Details" (Requires Decryption of `_enc` fields).
  • Write 1: "Submit Claim" (App calculates hashes and encrypts payloads).

A.2 Data Model

classDiagram class Claim { +ObjectId _id +Enum status } class CareePII { +String nino_enc +String nino_hash +String dob_enc } class BankDetailsPII { +String sort_code_enc +String account_enc } Claim "1" *-- "1" CareePII : embeds_Secure Claim "1" *-- "1" BankDetailsPII : embeds_Secure

A.3 Checklist Compliance Matrix

Checklist Item Implementation Decision Status
Blind Indexing `nino` is searchable. We store `nino_hash` (HMAC-SHA256) for exact matching. `nino_enc` is used for display only. PASSED
Encryption Strategy Application uses AES-256-GCM. DB receives only ciphertext. PASSED
Schema Validation Validator enforces presence of `_hash` fields for all PII blocks. PASSED
ESR Rule Search Index: `{ "caree_details.nino_hash": 1, "status": 1 }`. PASSED

A.4 Implementation Artifacts

Database-Level Schema Validation

db.createCollection("claims", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["status", "caree_details"],
      properties: {
        caree_details: {
          bsonType: "object",
          required: ["nino_enc", "nino_hash"], // Enforce Hash presence
          properties: {
            nino_enc: { bsonType: "string", description: "AES-256-GCM ciphertext" },
            nino_hash: { bsonType: "string", description: "HMAC-SHA256 for lookup" }
          }
        }
      }
    }
  }
})

Indexing Strategy

// 1. Support Caseworker Search: "Find claim by NINO"
// We index the HASH, not the encrypted data.
db.claims.createIndex({ "caree_details.nino_hash": 1 });

// 2. Support Dashboard: "Find by Claimant ID (Hashed) + Date"
db.claims.createIndex({ "claimant_id_hash": 1, "submission_date": -1 });

// 3. GDPR Retention
db.claims.createIndex({ "submission_date": 1 }, { expireAfterSeconds: 220752000 });
